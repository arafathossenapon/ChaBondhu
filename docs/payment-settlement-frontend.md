# Payment settlement frontend

From **My orders**, open an order and find **Payment settlement** below pickup and collection. The summary keeps the estimated harvest snapshot, measured weight, agreed price, and backend-calculated payable amount separate. Amounts are exact BDT decimal strings. PostgreSQL rounds the price times actual weight to two decimal places. The browser only formats the result.

## API mapping

| Screen or action                          | Endpoint                                                                    | Request                                                                               | Response and permissions                                                                                                                                                                                                                                                                        |
| ----------------------------------------- | --------------------------------------------------------------------------- | ------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Order context                             | `GET /orders/:id`                                                           | Order ID                                                                              | 200 with order, listing, participants, pickup, weight, and independent order/payment statuses. The participant routes are role-protected.                                                                                                                                                       |
| Payable amount and current payment status | `GET /payments/order/:orderId/amount`                                       | Order ID                                                                              | 200 with `orderId`, `amountBdt` as a string, `currency` and `paymentStatus`. Owning grower and factory can read collected or completed orders with a positive payable amount. 409 means the order is unavailable for settlement.                                                                |
| Attempt history                           | `GET /payments/order/:orderId/history`                                      | Optional `page` and `limit`                                                           | 200 with `data`, `total`, `page`, `limit`, `totalPages`. Both owners can see prior and current attempts with method, provider, reference, payment date, submission timestamp, decision timestamp and rejection reason. A 404 specifically saying “Payment not found” displays an empty history. |
| Factory submission                        | `POST /payments/order/:orderId/attempts`                                    | `Idempotency-Key` header and `{ method, paymentDate, provider?, reference? }`         | 201 with payment ID, order ID, exact amount, currency and attempt. Owning factory only, on a `COLLECTED` order with `PENDING` or `REJECTED` payment. A replay of the same payload and key returns the original submission response.                                                             |
| Grower receipt                            | `PATCH /payments/order/:orderId/attempts/:attemptId/confirm` and `…/reject` | Confirm with `{}` or reject with `{ rejectionReason }`, trimmed to 1–1,000 characters | 200 with the decided attempt. Owning grower only, for the open attempt on a `COLLECTED` order with `SUBMITTED` payment. Repeating an already successful confirmation is safe.                                                                                                                   |
| Factory completion                        | `PATCH /orders/:id/status`                                                  | `{ orderStatus: "COMPLETED" }`                                                        | 200 with updated order. Owning factory only, on a `COLLECTED` order with `CONFIRMED` payment and reserved listing. The backend marks the listing `SOLD` atomically.                                                                                                                             |

The backend also exposes settlement details and paginated participant settlements. This order screen uses the amount and history endpoints for the required data. Admin read endpoints are outside the participant UI.

## Validation and errors

- Cash permits an optional reference and omits the provider. Bank transfer requires provider and reference. Mobile financial service requires BKASH or NAGAD and a reference. Dates are calendar dates. The form sends no client-supplied amount. It records reported payment details for receipt review. The backend has no gateway, evidence upload, or transfer initiation.
- A submission uses a unique key for the reviewed payload. After timeouts, network errors, or unreadable responses, the dialog refreshes order, amount, and history before enabling a retry of that exact payload and key. An observed state change removes the stale write action. The draft and key are held in memory for the lifetime of the order screen.
- The shared session handles 401. Field and request errors are shown in the form. Forbidden, missing or conflicting state can trigger a refresh. The backend remains authoritative for ownership and transitions. Completion refreshes order, settlement and marketplace queries.
